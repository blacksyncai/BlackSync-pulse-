# Analytics dashboard

`/analytics` contains the original nine-card analytics layout: open deal value, closed-deal win rate, logged calls, tasks, upcoming work, won value by close date, monthly deal activity, top open deals, and stage groups. The day-to-day follow-up workspace is the default Dashboard at `/dashboard`, with `/sales-workspace` kept as a compatible alias. Dashboard and Analytics are available as shared tabs and sidebar links.

Sales analytics read configured pipeline stage fields, including custom won/lost labels, and separate currencies. Lost deals are excluded from open value. Win rate uses won divided by won plus lost. Monthly value charts group deals by creation month and their current state; they do not claim historical stage snapshots. Won-by-month requires a recorded close date and excludes future dates. Workspace-wide call/task/contact/meeting counts are labeled separately. Deal queries expose partial results and a Load more control.

Deployment now skips unrelated workflow/documentation changes. Subsequent frontend-only releases can reuse the last full server image when the currently deployed version matches the preceding commit. That base remains fixed across frontend releases to avoid growing a chain of application images. Shared/backend changes, missing base images, and uncertain state use a full build. Every release writes a public commit marker and deployment waits for that exact marker plus healthy CRM status; Railway API errors fail the job.

Validation: six analytics tests cover custom pipeline stages, lost deals, currency separation, missing/future close dates, monthly cohorts, and empty data. A Chromium fixture renders the actual dashboard page, data hook and original charts with mocked API/theme boundaries and checks nine cards, filters, currency, links, refreshing, partial-data handling, errors and mobile overflow. Nine build-target cases cover frontend reuse and safe fallback for backend/shared changes, missing images, and stale or invalid release markers. The workflow YAML, shell target selector and Python verifier are syntax-checked. Production build and rollout verification are separate checks.
